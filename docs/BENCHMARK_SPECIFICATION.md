# RepairBench Benchmark Specification


## Benchmarking AI Systems for Automated Program Repair


**Version:** 0.1  
**Status:** Research Specification  
**Project:** RepairBench  
**Author:** Ayoub Beriane  
**Year:** 2026


---


# 1. Purpose


RepairBench is a research benchmark and experimental framework for evaluating AI systems that automatically generate repairs for software defects.


The benchmark is designed around a central principle:


> **A successful automated repair should be evaluated not only by whether it passes the available tests, but by whether it correctly resolves the intended defect, remains robust under controlled conditions, achieves an appropriate effectiveness-to-cost tradeoff, and can be reproduced under documented experimental conditions.**


RepairBench therefore treats automated program repair as a multi-dimensional evaluation problem.


The benchmark is intended to support systematic comparisons between AI-based repair systems, conventional automated program repair systems, and different repair strategies.


---


# 2. Research Objective


The primary objective of RepairBench is to determine how reliably AI systems can automatically repair software defects and how their repair performance should be evaluated.


The benchmark investigates five principal questions:


1. **Correctness**  
   Does a generated patch actually repair the underlying defect?


2. **Robustness**  
   Does repair performance remain stable when irrelevant characteristics of the program are changed while its semantics are preserved?


3. **Efficiency**  
   What computational resources are required to obtain successful repairs?


4. **Reproducibility**  
   Can reported repair results be reproduced under documented experimental conditions?


5. **Test-Guided Repair**  
   Does iterative access to test feedback improve repair effectiveness, and what additional cost does it introduce?


---


# 3. Scope


RepairBench focuses on automated program repair systems that generate or modify source code in response to software defects.


The benchmark may evaluate:


- Large language models
- AI coding agents
- Code-generation models
- Conventional automated program repair systems
- Hybrid repair systems
- Single-shot repair systems
- Iterative test-guided repair systems


The benchmark may be applied to different:


- Programming languages
- Software projects
- Defect categories
- Model families
- Repair strategies
- Test suites


The exact languages, datasets, and models used in an experiment must be explicitly documented.

5. Terminology
5.1 Bug

A defect in a software program that causes the program to behave incorrectly with respect to its intended behavior.

5.2 Buggy Program

The original program containing the defect before repair.

5.3 Repair

A modification to the buggy program intended to resolve the identified defect.

5.4 Patch

A concrete source-code modification generated or applied by a repair system.

5.5 Candidate Patch

A patch generated by a repair system that has not yet been conclusively classified as correct or incorrect.

5.6 Test Suite

A collection of executable tests used to evaluate the behavior of a program.

5.7 Test-Suite Success

A condition in which the evaluated patch passes the tests included in the specified evaluation suite.

5.8 Plausible Repair

A generated patch that satisfies the benchmark's specified test-based acceptance criteria.

A plausible repair is not necessarily a correct repair.

5.9 Correct Repair

A repair that satisfies the stronger correctness criterion defined by the experiment and correctly resolves the intended defect without violating the intended behavior of the program.

5.10 Regression

A previously correct behavior that becomes incorrect as a consequence of a generated patch.

5.11 Semantics-Preserving Transformation

A transformation that changes the representation of a program while preserving its relevant observable behavior.

5.12 Repair Attempt

One execution of a repair process that produces one or more candidate patches.

5.13 Repair Iteration

One cycle in an iterative repair process consisting of patch generation, evaluation, and feedback.

5.14 Repair Budget

The maximum amount of computational or procedural effort that a repair system is permitted to use.

A budget may be expressed in:

Model calls
Candidate patches
Iterations
Tokens
Time
Monetary cost
Compute resources

10. Reference Repairs

Where a known human or canonical repair exists, it may be stored as a reference patch.

The reference patch is primarily an evaluation artifact.

It should not automatically be treated as the only possible correct implementation.

Different source-code implementations may correctly resolve the same defect.

Therefore:

Reference Patch
      ≠
Only Possible Correct Patch

The benchmark should distinguish reference similarity from behavioral correctness.

12. Test Categories
12.1 Existing Tests

Tests available to the repair system or part of the original project test suite.

12.2 Hidden Tests

13. Correctness Specification

Correctness is the primary evaluation dimension of RepairBench.

A repair should ideally satisfy all of the following:

Correct Repair
│
├── Resolves Intended Defect
├── Preserves Intended Behavior
├── Passes Required Tests
├── Avoids Regressions
└── Satisfies Additional Validation

The exact correctness criterion depends on the benchmark and available validation mechanisms.

14. Correctness Levels

RepairBench may classify repairs using multiple levels.

Level 0: Invalid

The generated patch cannot be evaluated because it fails to apply, compile, or execute as required.

Level 1: Test Failure

The patch applies but fails one or more required tests.

Level 2: Test-Suite Success

The patch passes the available test-based acceptance criteria.

This corresponds to a plausible repair unless stronger validation is available.

Level 3: Additional Validation Success

The patch passes additional validation beyond the original test suite.

Level 4: Validated Correct Repair

The patch satisfies the strongest correctness criterion available for the experiment.

The benchmark should report the exact validation mechanism used.

16. Behavioral Correctness

Where possible, RepairBench should evaluate whether the generated patch implements the intended behavior rather than merely reproducing the observed test outcomes.

Potential mechanisms include:

Behavioral specifications
Differential testing
Metamorphic testing

Regression suites
Independent validation

The selected mechanism must be documented.

17. Reference Patch Similarity

Textual similarity to a reference patch may be measured as an auxiliary metric.

However:

Patch Similarity
       ≠
Correctness

A correct repair may differ substantially from the reference implementation.

Similarly, a patch that closely resembles a reference patch may still be incorrect if it is incomplete or incorrectly applied.

18. Robustness Specification

Robustness measures whether repair performance remains stable when irrelevant aspects of a program are changed while its relevant semantics are preserved.

The core experimental comparison is:

Original Instance
       │
       ▼
Repair System
       │
       ▼
Original Performance

versus:

Transformed Instance
       │
       ▼
Repair System
       │
       ▼
Transformed Performance

The difference between these outcomes provides evidence about representation sensitivity.

19. Semantics-Preserving Transformations

Potential transformations include:

Variable renaming
Function renaming
Formatting changes
Whitespace changes
Equivalent syntactic constructs
Non-semantic comment changes
Statement-preserving transformations
Other validated transformations

Transformations must be validated independently.

20. Transformation Requirements

A transformation should satisfy the following conditions:

It must be deterministic when determinism is required by the experiment.
It must preserve the intended semantics.
It must not introduce unrelated defects.
It must preserve the benchmark's intended defect.
It must preserve required test behavior.
Its provenance must be recorded.
Its transformation method must be reproducible.
21. Transformation Validation

A transformed benchmark instance should be validated before being used in a robustness experiment.

A conceptual validation process is:

Original Program
      │
      ▼
Apply Transformation
      │
      ▼
Transformed Program
      │
      ▼
Run Validation Tests
      │
      ▼
Compare Behavior
      │
      ▼
Transformation Accepted / Rejected

A transformation should not be assumed to be semantics-preserving solely because its source code appears equivalent.

22. Robustness Metrics

The proportion of reported experimental results that can be reproduced under the documented conditions.

79. Separation of Generation and Evaluation

RepairBench should maintain a strict separation between:

Repair Generation

and:

Repair Evaluation

The repair system generates candidate patches.

The evaluator determines whether those patches satisfy the benchmark criteria.

This separation reduces the risk of evaluation logic being incorporated into the repair process unintentionally.

80. Candidate Identification

Every generated patch should receive a unique candidate identifier.

For example:

83. Fairness of Comparisons

If equal resources are impossible, the difference must be reported.

84. Cost-Effectiveness

RepairBench may evaluate the relationship between repair effectiveness and computational cost.

A system can therefore be characterized by:

      │

94. Threats to Validity

RepairBench recognizes several threats to validity.

94.1 Internal Validity

Potential threats include:

Incorrect benchmark preprocessing
Faulty transformations
Bugs in evaluation scripts
Configuration inconsistencies
Incorrect metric calculations
Test-environment differences
Unexpected model behavior

Mitigation should include automated validation and independent checks where possible.

94.2 External Validity

Results from a specific benchmark may not generalize to:

Other programming languages
Other software projects
Other defect classes
Other model families
Production environments

Claims should therefore remain proportional to the evaluated scope.

94.3 Construct Validity

A metric may not perfectly represent the underlying concept it intends to measure.

For example:

Test Passing
     ≠
Semantic Correctness

and:

Runtime
     ≠
Complete Computational Cost

Metrics should therefore be interpreted within their experimental context.

94.4 Transformation Validity

Robustness conclusions depend on the validity of semantics-preserving transformations.

If a transformation changes program behavior, differences in repair performance may be caused by the transformation itself rather than representation sensitivity.

94.5 Model Validity

AI model behavior may change between versions.

Results obtained from one model version should not automatically be attributed to an entire model family.

94.6 Dataset Validity

A benchmark may overrepresent particular:

Languages
Projects
Defect types
Complexity levels
Coding styles

This can influence measured repair performance.

99. Research Principles

RepairBench follows the following principles.

Principle 1: Separate Plausibility From Correctness

A test-passing patch should not automatically be described as a correct repair.

Principle 2: Measure Multiple Dimensions

Repair effectiveness should be evaluated alongside robustness, efficiency, and reproducibility.

Principle 3: Control Experimental Variables

Comparisons should isolate the factor being studied.

Principle 4: Record Experimental Configuration

Models, datasets, prompts, parameters, and evaluation procedures should be documented.

Principle 5: Preserve Experimental Artifacts

Where permitted, configurations, generated patches, logs, and results should be preserved.

Principle 6: Avoid Unsupported Claims

Conclusions should reflect the evidence actually produced by the experiment.

Principle 7: Report Negative Results

Failed repairs and unsuccessful experiments are part of the scientific evidence.

Principle 8: Make Results Reproducible

Experiments should be designed so that independent researchers can reconstruct them where practical.

107. Final Benchmark Principle

RepairBench is ultimately based on the following principle:

The ability of an AI system to generate a test-passing patch is only one part of automated program repair. A meaningful evaluation must also investigate whether the patch is correct, whether the system is robust to controlled changes, what resources are required to obtain the repair, and whether the reported result can be reproduced.

The benchmark therefore seeks to move automated program repair evaluation from:

"Did the tests pass?"

toward:

"Did the system produce a correct repair,
under controlled conditions,
with measurable cost,
and with results that can be reproduced?"

This distinction forms the methodological foundation of RepairBench.
